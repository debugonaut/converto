# macOS app: approved scope and implementation

The user approved the tool-hub image and requested implementation on Mac first.
Reference: `docs/design/macos-tool-hub-reference.png`. The landing page and CLI
ASCII identity are outside this change. This is a native Flutter desktop app.

## Experience

Charcoal surfaces, amber selection/actions, teal offline/success, native Mac
window controls. Tools and Recent navigation. Search and category filters lead
to focused workspaces for the 19 file operations already implemented by the
CLI. The six terminal utility commands become navigation/settings rather than
fake file tools. No cloud account, uploads, analytics, quotas or artificial
file-size restrictions. Processing capabilities and optional local codecs are
described honestly; no invented OCR, signature or arbitrary PDF text editor.

Drops select files; they never execute operations. Preserve order, deduplicate
repeated drops, reject links/unsupported files, and inspect folders shallowly.
Merge has explicit file ordering. Run requires an explicit action. Workspaces
show only relevant parameters, progress, errors, outputs and cancellation.
History is local, optional and clearable; passwords are never persisted.

## Architecture and safety

Typed tool catalog -> selection -> workspace -> single background isolate ->
shared FileOperations/PdfEngine. CPU/native work stays off the UI isolate.
Each job owns private staging under the selected destination. Publish completed
files with collision-safe names; originals are never overwritten. Failed or
cancelled jobs remove their staging. Cancellation is cooperative: stop after
the current engine call finishes, so native/helper cleanup always executes.
Do not kill an isolate in the middle of a native write.

Mac builds target macOS 13+. The downloadable preview uses a standard native
window and ad-hoc signing, not App Store signing/notarization. It is not App
Sandbox constrained because it interoperates with optional local CLI helpers;
the engine performs no network requests and downloads no runtime dependencies.
Production notarization requires the owner's Apple signing identity.

## Implementation sequence

1. Add the Mac runner and approved design tokens.
2. Add the typed catalog, safe file intake and worker/job lifecycle.
3. Build the tool hub, focused workspaces, local history and settings.
4. Exercise every GUI operation through the shared executor, plus repeated
   drops, paths, validation, batch failure/cancellation and widget flows.
5. Build the real app on macOS CI (this host lacks full Xcode), download and
   inspect it on this Mac. Record native validation and footprint separately
   from the existing CLI audit. Preserve and rerun CLI regression checks.
